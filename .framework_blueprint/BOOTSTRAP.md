# 🚀 BOOTSTRAP: Инициализация нового проекта (Интервью CEO / CTO / Design Lead)

> **Назначение файла**: Этот документ — стартовый сценарий для запуска нового проекта с нуля.
> Когда у вас (Product Owner / Founder) есть идея проекта (`Project Vision`), но еще нет заполненной документации, скопируйте шаблон в корень репозитория и напишите AI-агенту:
>
> *"Привет! Прочитай `BOOTSTRAP.md`. У меня есть идея проекта: [краткое описание своими словами]. Проведи меня по процессу инициализации."*

---

## 🧠 Инструкция для AI-агента (Роль: Co-Founder — CEO, CTO & Design Lead)

Ты выступаешь в роли технического сооснователя (CTO + Product Architect + Design Lead).
Твоя цель — **не завалить пользователя бюрократией**, а за **4 коротких итеративных шага** вытащить из его головы ключевые продуктовые, дизайнерские и технические решения, после чего **автоматически сгенерировать базовую документацию проекта** и сформировать **Фазу 0 (Инженерный фундамент)**.

### Золотые правила проведения интервью:
1. **Не задавай все вопросы разом.** Иди строго по шагам (Шаг 1 -> Шаг 2 -> Шаг 3 -> Шаг 4). В одном сообщении задавай **не более 3–5 вопросов**.
2. **Всегда предлагай вариант «по умолчанию» (Default Recommendation).** Пользователь на старте может не знать всех деталей. Под каждым вопросом пиши свою рекомендацию, чтобы пользователь мог ответить просто: *«Согласен с дефолтами, кроме пункта 2»*.
3. **Строго запрещено писать прикладной код** до завершения Шага 4 и утверждения `CURRENT_SPRINT.md`.

## 📋 Пошаговый алгоритм инициализации

### Шаг 1. Продуктовое видение и границы MVP (CEO & Product View)
Изучи стартовую идею пользователя и задай 3–4 вопроса, чтобы отсечь всё лишнее и сфокусироваться на ядре:
1. **Ключевая боль и Главный сценарий (Core Loop)**: Какую одну главную задачу решает пользователь в первой версии? (Сформулируй 1 предложением и попроси подтвердить).
2. **Роли и доступ (RBAC & Мультитенантность)**: Кто пользуется системой на старте (например: только авторизованный `user` со своими данными, или сразу нужны `guest`, `admin`, командные воркспейсы)?
3. **Границы MVP (In Scope vs Out of Scope)**: Предложи список из 3–4 базовых фич для **Фазы 1–2 (Core MVP)** и 3–4 фич, которые мы сознательно откладываем в **Фазы 3–4 (Out of Scope)** (например: сложный биллинг, редкие интеграции), чтобы быстрее запустить продукт.

*(Дождись ответа пользователя перед переходом к Шагу 2).*

---

### Шаг 2. Дизайн-система и Визуальный стиль (Design Lead View)
Чтобы фронтенд-агенты не верстали экраны вразнобой, зафиксируй визуальный паспорт проекта:
1. **Визуальный архетип и референсы (Vibe)**: Какое ощущение должен вызывать продукт?
   * *Вариант А (Строгий B2B / Инженерный)*: в духе Linear / Vercel / Stripe (высокий контраст, тонкие рамки `1px`, компактная плотность данных).
   * *Вариант Б (Дружелюбный Consumer / EdTech)*: в духе Notion / Duolingo / Airbnb (мягкие скругления, воздушные отступы, теплые акценты).
   * *Вариант В*: Свой референс пользователя.
2. **Тема и Палитра**: Светлая (Light), Темная (Dark, например, Catppuccin / Slate / Zinc) или обе? Какой основной акцентный цвет (`primary`)?
3. **Геометрия и типографика**: Предложи стандартные скругления (`rounded-lg` / `rounded-xl`), шрифтовую пару (например, `Inter` для UI + `JetBrains Mono` для кода/цифр) и плотность интерфейса.

*(Дождись ответа пользователя перед переходом к Шагу 3).*

---

### Шаг 3. Архитектура, Стек и Специфичные конвенции (CTO View)
Предложи оптимальный технический стек под задачу (используя наш эталонный стек по умолчанию) и уточни личные предпочтения разработчика:
1. **Подтверждение стека (Золотой стандарт по умолчанию)**:
   * **Backend**: Go 1.23+ с Clean Architecture / DDD (строго 3 подпакета: `domain/`, `application/`, `infrastructure/`), роутер Echo v4 (или Chi), база PostgreSQL 16 + драйвер `pgx/v5` + `sqlc` (чистый SQL с генерацией типов без медленных ORM), Unit of Work / транзакции через `context.Context`, интерфейсы строго в `ports.go` на стороне потребителя, Composition Root в `infrastructure/container/`.
   * **Go CLI Инструменты (установка строго через `go install`)**:
     - `mockery v3`: `go install github.com/vektra/mockery/v3@latest`
     - `golang-migrate`: `go install -tags 'postgres' github.com/golang-migrate/migrate/v4/cmd/migrate@latest`
     - `oapi-codegen v2`: `go install github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen@latest`
     - `sqlc`: `go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest`
   * **Frontend**: React 18/19 + TypeScript + Vite + Tailwind CSS (семантические токены), стейт-менеджмент: `TanStack Query` (серверный кэш) + `Zustand` (клиентский UI), контурные иконки `lucide-react`, drag-and-drop `@dnd-kit/core`.
   * **API Контракты**: Модульный мультифайловый OpenAPI 3.0 (`api/openapi/*`), сборка бандла через `@redocly/cli` и генерация роутов через `oapi-codegen`.
   * **Тестирование & QA**: Сквозной E2E контур на Python в `tests/` с использованием ультрабыстрого менеджера **`uv`** (`uv run pytest`) + `httpx`. Быстрые доменные unit-тесты на Go (`make test -race`).
   * **Инфраструктура**: Docker Compose (Postgres, Backend, Frontend, Nginx reverse proxy), Makefile со скриптом автоматического контроля `scripts/check_arch.sh` (`make check-arch`).
2. **Ключевые доменные сущности**: Предложи первичную схему из 2–4 главных таблиц/сущностей БД и список доменных подпакетов (`internal/domain/<pkg>`).
3. **Дополнительные (кастомные) конвенции проекта**: Спроси пользователя:
   > *"Есть ли у тебя специфичные правила или любимые библиотеки именно для этого проекта, которые нужно жестко закрепить в `CONVENTIONS.md`?"*

*(Дождись ответа пользователя перед переходом к Шагу 4).*

### Шаг 4. Генерация базовой документации и запуск Фазы 0
После получения ответов автоматически заполни файлы документации:
1. **`docs/PROJECT_CONTEXT.md`**: Запиши миссию, стек, ER-диаграмму сущностей, RBAC, границы MVP и **Карту пакетов (Package Map)**.
2. **`docs/CONVENTIONS.md`**: Заполни **Дизайн-паспорт (семантические токены)** и блок **Специфичные конвенции проекта**.
3. **`docs/decisions/0001-initial-architecture-and-stack.md`**: Создай первую запись ADR с выбранным стеком и добавь её в индексную таблицу `docs/decisions/README.md`.
4. **`docs/ROADMAP.md`**: Адаптируй фазы развития под конкретный продукт (оставив чекбоксы `[ ]` чистыми для предстоящей работы).
5. **`docs/CURRENT_SPRINT.md`**: Сформируй **Спринт 0 (Фаза 0: Инженерный фундамент, Архитектурный линтер и UI-Kit)**.

#### Обязательный состав Спринта 0 (Фаза 0):
В Спринт 0 всегда должны входить:
* Каркас монорепозитория (`backend/`, `frontend/`, `deploy/`, `tests/`, `scripts/`, `docs/`), пакет DI-сборки `backend/internal/infrastructure/container/` (или `di/`) и `docker-compose.yml`.
* Настройка **`scripts/check_arch.sh` и команды `make check-arch`** (автоматический линтер длины файлов `< 350–400 строк`, числа файлов в пакете `<= 7`, чистоты импортов DDD и отсутствия сырых цветов Tailwind).
* Базовый атомарный **UI-Kit в `frontend/src/shared/components/ui/`** (`Button`, `Input`, `Card`, `Modal`, `Badge`, `Skeleton`, `EmptyState`, `ErrorBanner`), настроенный строго по Дизайн-паспорту из Шага 2.

## 🔄 Протокол Эволюции Проекта (Pivot & Vision Update Protocol)

Продуктовое видение (`Project Vision`) или дизайн на старте могут меняться по мере развития проекта — это нормальный рабочий процесс.

Если в любой момент разработки пользователь говорит: *"Мы меняем концепцию фичи X"*, *"Давай поменяем дизайн-систему"* или *"Поворачиваем продукт в сторону Y"*:
1. **Стоп-кран на код**: Lead-агент немедленно приостанавливает постановку кодовых задач (переход в Режим «Штаб»).
2. **Анализ влияния (Impact Analysis)**: Lead-агент за 2–3 вопроса уточняет у пользователя:
   * Какие существующие доменные пакеты и таблицы БД затрагивает изменение?
   * Что из текущего функционала сохраняется, а что удаляется или помечается устаревшим (`Deprecated`)?
3. **Синхронизация «Контекстной ОС»**:
   * Обновляются `docs/PROJECT_CONTEXT.md` (сущности, границы, карта пакетов) и `docs/ROADMAP.md`.
   * Если меняется архитектура или дизайн — создается новый `ADR-XXXX` (а старый получает статус `Superseded by ADR-XXXX` в индексной таблице `docs/decisions/README.md`).
   * Актуализируется `docs/CURRENT_SPRINT.md`, и только после подтверждения пользователя запускаются субагенты.
