# ADR-0002: Стратегия сессионной JWT-аутентификации, Tenant Isolation и онбординга

* **Дата**: `2026-10-14`
* **Статус**: `Accepted`
* **Инициатор / Автор**: `Pavel (Founder) & Lead AI Architect (Co-Founder)`
* **Затрагиваемые подсистемы / пакеты**: `backend/internal/domain/workspace`, `backend/internal/infrastructure/http`, `api/openapi/*`, `frontend/src/*`

---

## 🎯 1. Контекст и Проблема (Context & Problem Statement)

Для перехода к Этапу 1.1 (Фаза 1) требуется реализовать систему аутентификации пользователей, создание персонального рабочего пространства (Personal Workspace) и изоляцию данных между тенантами (Tenant Isolation). Необходимо определить:
1. Способ безопасной передачи и хранения сессионных токенов (защита от XSS и CSRF в Web SPA и удобство автотестов).
2. Механизм автоматической инициализации личного пространства при регистрации.
3. Гарантии изоляции данных между воркспейсами на уровне SQL и роутинга Echo.

---

## 🔍 2. Рассмотренные варианты (Considered Options)

### Вариант 1: Гибридный JWT (HTTP-only Cookie с SameSite=Lax + Fallback на Authorization Bearer Header) (Выбран)
* **Суть**: При аутентификации сервер выставляет JWT токен в `HttpOnly; Secure; SameSite=Lax; Path=/` Cookie, а также возвращает токен в JSON-ответе.
* **Плюсы (+)**:
  - Максимальная безопасность в Web SPA: JavaScript не имеет прямого доступа к токену через `document.cookie`, что полностью нивелирует угрозу кражи сессии через XSS.
  - Удобство E2E и REST клиентов: фикстуры `pytest` и curl могут передавать заголовок `Authorization: Bearer <token>`.
  - Защита от CSRF благодаря `SameSite=Lax` для браузерных переходов и стандартных запросов.
* **Минусы (-)**:
  - Необходимость поддержки двух источников токена в Echo middleware (сначала Cookie, затем Header).

### Вариант 2: Исключительно LocalStorage + Bearer Header
* **Суть**: Токен хранится в `localStorage` браузера и передается только в заголовке `Authorization`.
* **Плюсы (+)**: Простая реализация на фронтенде.
* **Минусы (-)**: Высокая уязвимость к XSS (любая сторонняя библиотека в `node_modules` может прочитать `localStorage.getItem('token')`).

---

## 🏆 3. Принятое решение и Обоснование (Decision Outcome)

Выбран **Вариант 1**:
1. **Передача токена**:
   - Web SPA использует автоматическую передачу через `HttpOnly` Cookie.
   - Тесты и API-интеграции могут использовать заголовок `Authorization: Bearer <token>`.
2. **Инициализация онбординга**:
   - При успешной регистрации пользователя атомарно в транзакции создается:
     1. Запись `users` (пароль хешируется через `bcrypt`).
     2. Запись `workspaces` с типом `personal` и именем «Личное».
     3. Запись `workspace_members` с ролью `owner`.
     4. 2–3 приветственные задачи в `tasks` во «Входящих» (Inbox), обучающие горячим клавишам `J/K` и круглому чекбоксу.
3. **Tenant Isolation**:
   - Echo middleware валидирует JWT, извлекает `user_id` и активный `workspace_id` и помещает их в `context.Context`.
   - Все SQL-запросы к сущностям `tasks`, `projects`, `automations` содержат предикат `WHERE workspace_id = $1` с проверкой членства пользователя.

---

## ⚡ 4. Последствия и Риски (Consequences & Risk Mitigation)

* **Положительные**:
  - Нулевой фрикшн онбординга: пользователь сразу после регистрации попадает в готовый, наполненный тактильный интерфейс с задачами в Inbox.
  - Надежная безопасность и чистота мультитенантности.
* **Смягчение рисков**:
  - В dev-режиме флаг `Secure` в cookie отключается, если запрос идет по незашифрованному HTTP на `localhost`.
